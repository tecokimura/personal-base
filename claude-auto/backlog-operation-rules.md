# Backlog Operation Rules

- Status: Decided
- Owner: Keith / Codex
- Last Updated: 2026-05-18

## 目的

このプロジェクトにおける Backlog の使い方、`docs/` との役割分担、課題起票ルールを固定し、運用の混線を防ぐ。

## 最重要ルール

- 仕様、設計、ロードマップ、論点整理、運用ルールの正本は常に `docs/` に置く
- Backlog は実行管理、進捗管理、担当管理、レビュー待ち管理のために使う
- Backlog の Wiki / Document は、Backlog 内で参照しやすくするための補助用途に限定する
- Backlog の Wiki / Document にだけ重要ルールを書かない
- `docs/` と Backlog の記載が矛盾した場合は、`docs/` を正とする

## 使い分け

### `docs/` に書くもの

- プロダクト仕様
- 技術設計
- ADR
- ロードマップ
- 実装計画
- 決定待ち課題
- Backlog 運用ルールそのもの

### Backlog に書くもの

- マイルストーン
- 親課題、子課題
- 課題の担当者、状態、期限
- 実装や設計の実行単位
- 作業の依存関係
- 実行時のメモ
- レビュー結果、確認結果、完了判断の記録

### Backlog Wiki / Document に書いてよいもの

- Backlog 利用者向けの短い運用メモ
- マイルストーンの簡易な説明
- `docs/` へのリンク集

### Backlog Wiki / Document に書かないもの

- 正本として扱う仕様
- `docs/` に未反映の重要決定
- 課題分解ルールやステータス運用ルールの唯一の保管場所

## マイルストーン運用

- マイルストーンは機能別ではなく、時系列ベースで管理する
- ただし、名前だけで内容が分からない状態は避ける
- 命名は `MVP-<到達点>` または `Phase N-<到達点>` を基本とする
- 初期設定として、次の 3 つを採用する

- `MVP-基盤構築`
- `MVP-業務コア実装`
- `Phase 2-拡張機能`

例:

- `MVP-基盤構築`
- `MVP-業務コア実装`
- `Phase 2-拡張機能`

マイルストーンの説明が必要な場合は、`docs/roadmap.md` を正本にし、Backlog 側には短い要約と `docs/` への参照だけを書く。

## ガントチャート運用

- ガントチャートは、厳密な工数見積もり表ではなく、実装順と詰まりの可視化に使う
- 親課題には原則として `開始日` と `期限` を入れ、全体の流れを見えるようにする
- 子課題は、直近で着手するものから順に `開始日` と `期限` を入れる
- 日付未確定の子課題は、無理に日付を入れず未設定のまま扱ってよい
- 通常確認するガント表示では、`未対応`、`対応中`、`レビュー待ち` を主対象とし、`完了` は必要時のみ表示する
- ガントの主な見方は `マイルストーン` 単位または `担当者` 単位とする
- `MVP-基盤構築` と `MVP-業務コア実装` の流れが一目で見える状態を優先する

## Wiki 運用

- Backlog の Wiki は仕様の正本にせず、Backlog 利用者の入口ページとして使う
- Wiki には `docs/` の要約を複製せず、参照先リンクと短い運用メモだけを書く
- Wiki の役割は、現在地、運用ルール、参照先、今見るべき課題への導線整理とする
- 設計内容や重要判断は必ず先に `docs/` に反映し、Wiki にはその参照だけを置く
- `PMO_PJPERSONALBASE` の Wiki では、少なくとも `今の進め方`、`設計の正本リンク集`、`Backlog運用ルール`、`実装着手中の論点` を持つ

## 課題階層

- 親課題は機能領域を表す
- 子課題は設計、実装、検証の実行単位を表す

親課題の基本単位:

- `認証・認可基盤`
- `組織管理`
- `社員台帳管理`
- `組織図表示`

## 起票粒度

- 1 課題は、1 つの完了条件で閉じられるレビュー単位にする
- 原則として、1 課題は 1 本の PR 相当を目安にする
- 別 AI にそのまま依頼できる粒度にそろえる
- 実装側へ新規に追加依頼する場合は、原則として新しい課題を起票して渡す
- 「認証全部」のような広すぎる単位では起票しない
- 「カラム 1 個だけ」のような細かすぎる単位にも分けすぎない

推奨する作業単位:

- `schema`
- `migration`
- `backend API`
- `frontend UI`
- `test`
- `設計補足`
- `ADR化`

## 課題種別運用

- 原則として通常の設計、実装、検証作業は `タスク` を使う
- 実装後に見つかった不具合だけ `バグ` を使う
- MVP 外や後続改善候補は `要望` を使う
- `その他` は原則使わない

初期運用では、ほとんどの起票を `タスク` に寄せる。

## 優先度運用

- `高`: 現在の実装着手や直近依存に必要な課題
- `中`: 近いうちに必要だが、直近のブロッカーではない課題
- `低`: 後続フェーズ、改善候補、調査メモ寄りの課題

初期運用では、`docs/implementation-plan.md` の直近対象は基本 `高`、`Phase 2` の課題は原則 `中` または `低` とする。

## 担当運用

- 初期起票時点では担当は `未割当` を基本とする
- 実際に着手するタイミングで担当を設定する

起票時点では計画管理を優先し、担当の先付けで運用を複雑にしない。

## 期限運用

- 初期起票時点では期限は空欄を基本とする
- 期限は、マイルストーン内で着手順と依存関係が固まってから設定する

初期運用では、期限よりもマイルストーンと優先度を優先して管理する。

## ステータス運用

Backlog の標準ステータス名と完全一致しなくても、以下の意味で運用する。

- `未対応`: 着手前
- `対応中`: 実作業中
- `レビュー待ち`: 実装または文書更新は終わり、確認待ち
- `完了`: レビューや確認まで完了
- `保留`: 依存関係や判断待ちで止まっている

Backlog 側で標準状態に合わせる場合の読み替え:

- `未対応` -> `未対応`
- `対応中` -> `処理中`
- `レビュー待ち` -> `処理済み`
- `完了` -> `完了`
- `保留` -> `保留`

## カテゴリ運用

ステータスだけでは表現できないフェーズを、カテゴリで補完する。
カテゴリは MCP の `get_categories` で ID を取得し、`update_issue` の `categoryId` で付け外しする。カスタムステータスは使わない。

### カテゴリ一覧

| カテゴリ | 組み合わせるステータス | 意味 | 次のアクション担当 |
|---|---|---|---|
| `実装待ち` | 未対応 | 仕様確定・実装開始待ち | 実装セッション |
| `レビュー待ち` | 処理済み | 実装完了・コードレビュー待ち | PM セッション |
| `修正待ち` | 処理中 | レビューNG・修正実装待ち | 実装セッション |
| `仕様確認待ち` | 処理済み | 実装ブロック中・仕様や方向性の判断が必要 | **ユーザー** |
| `動作確認待ち` | 処理済み | レビューOK・ユーザー動作確認待ち | **ユーザー** |

ユーザーが介入すべき課題は `仕様確認待ち` と `動作確認待ち` の 2 カテゴリで絞り込める。

### カテゴリ付け替えのタイミング

| タイミング | 操作 |
|---|---|
| タスク登録時（仕様確定済み） | 未対応 + `実装待ち` を付ける |
| 実装開始時 | `実装待ち` を外す → 処理中（カテゴリなし） |
| 実装完了時 | 処理済み + `レビュー待ち` を付ける |
| レビューNG 時 | 処理中 + `修正待ち` を付ける（`レビュー待ち` を外す） |
| 修正完了時 | 処理済み + `レビュー待ち` を付ける（`修正待ち` を外す） |
| レビューOK 時 | 処理済み + `動作確認待ち` を付ける（`レビュー待ち` を外す） |
| 仕様が不明で実装停止時 | 処理済み + `仕様確認待ち` を付ける |
| 仕様確認後・実装再開時 | `仕様確認待ち` を外す → 処理中（カテゴリなし） |
| ユーザー動作確認完了時 | 完了（カテゴリを外す） |

## ワークフロー全体像

```
ユーザーが仕様・方向性を決定
    ↓
PM セッション: docs 更新 → Backlog タスク登録
    （未対応 + 実装待ち）
    ↓
実装セッション: 実装開始
    （処理中）
    │
    ├─ 仕様が不明確 ──→ 処理済み + 仕様確認待ち
    │                        ↓
    │                   ユーザーが仕様を決定
    │                        ↓
    │                   PM セッション: docs 更新 → 実装再開
    │
    └─ 実装完了 ──→ 処理済み + レビュー待ち
                        ↓
                   PM セッション: コードレビュー
                        │
                        ├─ NG → 処理中 + 修正待ち → 実装セッションへ
                        │                ↓
                        │       修正完了 → 処理済み + レビュー待ち（繰り返し）
                        │
                        └─ OK → 処理済み + 動作確認待ち
                                    ↓
                               ユーザーが動作確認
                                    ├─ 不具合 → 新規課題登録 → 実装セッションへ
                                    └─ OK → 完了
```

レビュー運用ルール:

- レビューを実施したら、対象課題に必ずコメントを残す
- レビュー完了時は、指摘有無にかかわらず「レビューしたこと」「結果」「残課題の有無」をコメントに記録する
- 再レビュー時も同様に、その回の結論を対象課題へ追記する

レビュー確認ルール:

- ルートや API エンドポイントの不一致を指摘する前に、対象文字列を `rg` でコードベース全体検索して定義箇所を確認する
- controller 1 ファイルだけで結論を出さず、`admin` 系、通常系、関連 module を含めて並存実装の有無を確認する
- 実装差分の指摘は、必要に応じて関連 `docs/` の手順書や運用文書とも照合してから確定する
- 再レビューでは前回レビューコメントを鵜呑みにせず、毎回コードを一次情報として確認する
- 確認が不十分な仮説段階では断定コメントを書かず、「要再確認」として扱う

## 課題タイトル命名規則

- 形式は `[親課題名][作業種別] 内容` を基本とする

例:

- `[認証・認可基盤][schema] Employee の最小 Prisma モデルを追加`
- `[認証・認可基盤][API] ログイン API の最小実装を追加`

## 課題説明テンプレート

```md
## 起票メタ情報
- 起票元: 仕様検討 / 実装
- 起票主体: Codex / Claude / Keith
- 起票理由: 新規設計論点 / 実装中の不足発見 / 不具合 / 運用タスク

## 背景
- なぜこの作業が必要か
- 関連する機能領域やマイルストーン

## 作業内容
- 実施する変更内容
- 対象レイヤー

## 完了条件
- 完了とみなす条件
- 必要なら確認観点

## 参照ドキュメント
- docs/xxx.md
- docs/yyy.md

## 依存関係
- 先に必要な課題
- 同時進行で注意すべき課題

## 保留事項・Open Questions
- 未確定事項
- 判断が必要な論点
```

## 起票元の識別ルール

- すべての課題本文の先頭に `起票メタ情報` を入れる
- `起票元` は `仕様検討` または `実装` の 2 値で固定する
- `起票主体` は実際に課題化した主体を記録し、現時点では `Codex`、`Claude`、`Keith` のいずれかを使う
- `起票理由` は、なぜその課題が発生したかを短く残す
- 課題タイトルには起票元を入れず、検索しやすさと一覧性を優先して本文で管理する
- 起票後に別の担当者へ引き継いでも、`起票元` と `起票主体` は変更しない

起票メタ情報の例:

```md
## 起票メタ情報
- 起票元: 仕様検討
- 起票主体: Codex
- 起票理由: 設計文書の Open Questions を実行管理へ落としたため
```

```md
## 起票メタ情報
- 起票元: 実装
- 起票主体: Claude
- 起票理由: 実装中に追加対応が必要と判明したため
```

## 運用上の注意

- 重要な判断を先に `docs/` へ反映してから、Backlog の課題や Wiki に展開する
- Backlog 起票時は、必ず `docs/` の参照先を課題本文へ入れる
- 課題だけを読んでも着手できる状態にするが、仕様の全文は Backlog に複製しない
- `起票元 = 仕様検討` の課題は、対応する `docs` 正本が先に存在することを前提にする
- 実装側とのやりとりは、原則として Backlog の課題コメント上で行う
- 実装側へ別件を追加で依頼したくなった場合は、コメントで横流しせず新規課題として切り出す
- `起票元 = 実装` の課題は、実装中に見つかった不足や追加対応であることを `起票理由` に残す
- 運用ルールを変更する場合は、この文書を先に更新する
