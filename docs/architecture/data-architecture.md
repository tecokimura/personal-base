# Data Architecture

- Status: In Review
- Owner: Keith / Codex
- Last Updated: 2026-04-22

## 目的

データ保存、検索、履歴、分析の基本方針を決める。

## 背景

人材情報は更新、参照、検索、分析、監査の要求が混在しやすく、単純な CRUD 設計では破綻しやすい。

## 前提

- 個人情報を含む
- 履歴管理と検索要件が重要になる可能性が高い
- MVP の中心ユースケースは `社員台帳と組織図の一元管理`
- 顔写真は `Employee` の表示情報として扱う
- 顔写真はデフォルト画像ありの任意設定とする

## 決定事項

- MVP では、顔写真はストレージ抽象化の上に保存し、DB には参照のみを持つ
- 初期はローカルファイル保存を第一候補とする
- 将来は別サーバや `S3` 互換ストレージへ切り替え可能な形にする
- MVP と第 2 フェーズの主要データストアは `PostgreSQL` を第一候補とする
- 初期の検索は RDB 中心で始め、専用検索基盤は将来要件が明確になった時点で検討する

### `PostgreSQL` を第一候補とする理由

- 組織ツリーや組織スコープ判定で、再帰クエリや集約を扱いやすい
- `RBAC + 組織スコープ`、`WorkHistory`、監査ログのような複雑な参照要件に対応しやすい
- JSON, CTE, 部分インデックスなど、後続フェーズの拡張余地が広い
- マルチテナント SaaS の一般的な知見が多く、設計上の逃げ道を持ちやすい

### `MariaDB` を第一候補にしない理由

`MariaDB` でもこのプロダクトを成立させること自体は可能である。ただし、今回は単純な CRUD よりも、組織階層, 権限制御, 履歴, 監査, 将来の検索拡張との相性を重視する。

その観点では、初期から `PostgreSQL` を選ぶ方が後戻りしにくいと考える。

## 検討した選択肢

- RDB 中心
- RDB + 検索基盤
- RDB + データウェアハウス

## Open Questions

- 履歴をスナップショット型で持つか、イベント型で持つか
- 検索要件のために専用インデックスをどの時点で持つか
- 分析用途のデータ分離をいつ行うか

- `PostgreSQL` 前提のテーブル設計方針
- 履歴モデル
- 検索方式

## 履歴管理のたたき台

MVP でも、人材データの変更履歴をまったく持たないのは危険である。特に、所属、兼務、組織責任者は「いつ誰がどう変わったか」を後で確認できる必要がある。

ただし、最初から全変更をイベントソーシングのように管理すると実装が重くなりすぎる。そのため、MVP では「履歴が重要な対象だけ明示的に持つ」方針を第一候補とする。

### 選択肢 1. 現在値のみを持ち、履歴は持たない

利点:

- 実装が最も軽い
- 画面やAPIが単純になる

欠点:

- 異動や兼務の経緯が追えない
- 監査や運用確認で困る
- 後から履歴を追加すると移行が面倒

### 選択肢 2. 一部のエンティティだけ履歴を持つ

例:

- `Employment` は `Start Date / End Date / Status` で履歴的に持つ
- `OrganizationLeader` も `Start Date / End Date / Status` で履歴的に持つ
- `Employee` の基本情報変更は最新版のみ持つ

利点:

- MVP として現実的
- 組織・所属変更の履歴を追える
- 重要箇所だけ先に守れる

欠点:

- すべての項目の変更履歴は残らない
- 基本属性の過去値比較は難しい

### 選択肢 3. 汎用監査ログまたはイベント履歴を全体に持つ

例:

- 変更前後JSON
- 更新者
- 更新日時
- 対象エンティティ

利点:

- 変更を広く追える
- 監査要求に強い

欠点:

- 設計と実装が重い
- MVP でやるには過剰になりやすい

### 現時点の第一候補

MVP では、`選択肢 2. 一部のエンティティだけ履歴を持つ` を第一候補とする。

具体方針候補:

- `Employment` は履歴を前提としたエンティティとして扱う
- `OrganizationLeader` も履歴を前提としたエンティティとして扱う
- `Employee` の基本属性は最新版を保持し、汎用の過去履歴は MVP では持たない
- 必要に応じて、更新者と更新日時だけは基本テーブルに持つ
- 履歴の開始日や終了日は、事後対応として組織管理者が補正できるようにする
- 在籍しなくなった社員データは物理削除せず、論理削除で保持する

### MVP で履歴を持つ対象

- 主所属/兼務の開始・終了
- 上長変更
- 組織責任者の開始・終了
- 在籍状態の変更
- 論理削除された社員の在籍終了状態

### MVP で履歴を持たない対象

- 氏名変更の完全履歴
- 顔写真の完全履歴
- 表示名や軽微な表示項目の完全履歴
- すべての項目の変更前後JSON

### 現時点の考え方

- 人事台帳として意味が大きい「所属」「責任者」「在籍」は履歴を持つ
- それ以外は最新版中心でまず進める
- 汎用監査ログは別論点として後続で整理する
- 履歴は厳密な不変イベントログではなく、事後補正可能な業務履歴として扱う
- 退職や離任でも物理削除はせず、論理削除で過去データを残す
- 将来の `WorkHistory` では、少なくとも `updated_by` と `updated_at` を持ち、補助編集の痕跡を追える形が望ましい

### 論理削除の第一候補

- `Employee` に `deleted_at` または `is_deleted` を持つ
- 在籍しなくなった社員も検索対象からは通常除外しつつ、権限のある組織管理者は過去データを閲覧できるようにする
- `Employment` や `OrganizationLeader` の履歴は削除せず保持する

### 組織管理者による事後補正の考え方

- 履歴の補正対象は、開始日、終了日、上長、主所属/兼務、組織責任者とする
- 補正は既存履歴の直接上書きではなく、更新日時と更新者を残せる形が望ましい
- MVP では汎用監査ログまでは持たなくても、最低限 `updated_at` と `updated_by` は保持する方向が望ましい

## ログイン履歴と編集履歴のたたき台

将来的に人材情報を扱う以上、ログイン履歴と編集履歴は欲しくなる。ただし、MVP で広い監査ログまで入れると実装が重くなりやすい。

### 現時点の考え方

- ログイン履歴と汎用編集履歴は、MVP の必須対象にはまだ置かない
- ただし、第 2 フェーズで早めに入れる候補として扱う
- `WorkHistory` のように補助編集が発生する対象は、個別に `updated_by` を最初から持つ

### 推奨導入タイミング

- `LoginHistory` は第 2 フェーズで導入する
- `EditHistory` も第 2 フェーズで導入する

理由:

- MVP ではまず `社員台帳と組織図` に集中した方がベータ到達が早い
- 一方で、第 2 フェーズでは `WorkHistory` や社員自身の入力が増え、誰がいつ操作したかを追いたくなる
- 今回は差分保持までは不要なので、`時刻 + 操作者 + 対象` の追跡だけなら実装コストを比較的抑えられる
- `HR_ADMIN` や `MANAGER` による補助編集が発生するため、`WorkHistory` 導入より先、または同時期に編集履歴を持つ方が運用説明もしやすい

### 将来の第一候補

- `LoginHistory`
  - Employee ID
  - Logged In At
  - IP Address
  - User Agent
- `EditHistory`
  - Entity Type
  - Entity ID
  - Action Type
  - Changed By
  - Changed At
  - Scope Summary

### 最小カラム案

第 2 フェーズの最小版では、差分本文は持たず、まずは「誰が、いつ、何に対して、何をしたか」を追える形に絞る。

#### `LoginHistory`

- `tenant_id`
- `employee_id`
- `logged_in_at`
- `ip_address`
- `user_agent`

#### `EditHistory`

- `tenant_id`
- `entity_type`
- `entity_id`
- `action_type`
- `changed_by_employee_id`
- `changed_at`
- `scope_summary`

### `action_type` の第一候補

- `create`
- `update`
- `delete`
- `restore`

補足:

- `login` は `LoginHistory` 側で扱う
- 差分本文や変更前後 JSON は初期版では持たない

### 閲覧権限の第一候補

- `LoginHistory` と `EditHistory` の閲覧は、まず `HR_ADMIN` のみに許可する
- `ORG_ADMIN`、`MANAGER`、`EXECUTIVE_VIEWER`、`EMPLOYEE` には初期段階では許可しない

### `EditHistory` の対象エンティティ第一候補

- `Employee`
- `Employment`
- `OrganizationLeader`
- `WorkHistory`
- `RoleAssignment`

理由:

- 人事台帳、所属、責任者、権限、業務履歴は変更の意味が大きい
- 日常的に参照しなくても、「記録されている」という抑止力として価値がある
- 初期段階で対象を広げすぎず、重要変更に絞ることで実装負荷を抑えられる

### 保存先の第一候補

- 監査ログは DB テーブル保存を基本とする
- ただし、保存先は固定せず、標準出力や syslog のような出力先へ拡張できるようにする

理由:

- 初期の検索や画面閲覧は DB 保存が最も扱いやすい
- 一方で、運用やインフラ要件によっては標準出力や syslog へ流したくなる
- そのため、`AuditLogSink` のような抽象化を置き、DB / stdout / syslog を切り替えまたは併用できる形が望ましい

### 将来の出力先候補

- DB テーブル
- 標準出力
- syslog

### 保持期間の第一候補

- `LoginHistory` の初期保持期間は `365 日`
- `EditHistory` の初期保持期間は `1825 日 (5 年)`
- どちらもシステム設定または管理者向けサービス設定で変更できるようにする

理由:

- `LoginHistory` は件数が増えやすく、直近 1 年あれば運用確認や不正アクセス確認として十分なことが多い
- `EditHistory` は監査や抑止力として長く残す価値が高い
- 差分本文を持たない前提なら、`EditHistory` は 5 年保持でも現実的である

### 設定値の第一候補

- `login_history_retention_days`
- `edit_history_retention_days`

## 顔写真の保存方式たたき台

顔写真は `Employee` に紐づく表示資産であり、テキスト属性とは性質が異なる。そのため、通常の業務項目と同じ保存方法にすると後で扱いづらくなる。

### 選択肢 1. RDB にバイナリで保存する

利点:

- 実装が一見単純
- 参照先管理が不要

欠点:

- DB サイズが増えやすい
- 一覧表示や配信時に非効率
- 将来の画像変換やCDN連携に不向き

### 選択肢 2. オブジェクトストレージに保存し、DB には参照のみ持つ

例:

- DB: `photo_storage_key`, `photo_url`, `photo_updated_at`
- 保存先: S3 互換ストレージなど

利点:

- 一般的で拡張しやすい
- 画像サイズや配信に対応しやすい
- デフォルト画像や差し替えも扱いやすい

欠点:

- ストレージ参照管理が必要
- アップロード処理が少し増える

### 選択肢 3. 外部画像URLのみを持つ

利点:

- 実装が軽い
- ストレージを持たなくてよい

欠点:

- リンク切れや外部依存が発生する
- セキュリティと可用性が不安定
- 社内向け人材DBには不向き

### 現時点の第一候補

MVP では、`選択肢 2. オブジェクトストレージに保存し、DB には参照のみ持つ` を本番系の第一候補とする。

理由:

- MVP でも一覧表示やプロフィール表示で画像配信が発生する
- DB と画像資産を分けた方が運用しやすい
- 将来のリサイズ、キャッシュ、アクセス制御に拡張しやすい

ただし、開発環境では必ずしも外部ストレージを用意できるとは限らない。そのため、アプリケーションは保存先を抽象化し、ローカルファイル保存でも同じインターフェースで動くようにする。

### `Employee` に持つ項目の第一候補

- `photo_storage_key`
- `photo_storage_type`
- `photo_variant`
- `photo_updated_at`

必要なら表示用URLはアプリケーション側で生成する。

### 保存先の実行環境別方針

#### 本番/本番相当環境

- オブジェクトストレージを使う
- `photo_storage_type = object_storage`

#### 開発環境 / Docker / 最小構成

- 同一マシンまたは Docker ボリューム上のローカルファイル保存を許容する
- `photo_storage_type = local_file`
- 参照先はアプリケーション配下のアップロードディレクトリ、またはマウントボリュームとする

### ストレージ抽象化の考え方

- アプリケーションは `PhotoStorage` のような抽象インターフェース経由で保存・取得する
- 実装として `ObjectStoragePhotoStorage` と `LocalFilePhotoStorage` を切り替えられるようにする
- これにより、開発時は外部クラウドなしで動作し、本番ではオブジェクトストレージへ移行しやすくなる

### デフォルト画像の扱い

- 顔写真未設定時は共通のデフォルト画像を表示する
- デフォルト画像は個別社員データとして保存しない
- `photo_storage_key` が未設定ならデフォルト画像を返す

### 現時点の考え方

- 顔写真は人事マスタ本体ではなく付随資産として扱う
- DB には画像本体ではなく参照情報だけ持つ
- MVP では高度な画像加工や複数サイズ生成までは必須にしない
- 保存先は固定実装にせず、環境に応じて切り替え可能にする

### この判断の理由

- MVP でも一覧表示やプロフィール表示で画像参照が発生する
- DB 本体に画像を入れるより、運用と拡張がしやすい
- 将来のキャッシュ、変換、アクセス制御に発展させやすい
- 開発環境ではクラウド依存を減らし、Docker 単体でも動く方が扱いやすい
