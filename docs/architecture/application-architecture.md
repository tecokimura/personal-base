# Application Architecture

- Status: In Review
- Owner: Keith / Codex
- Last Updated: 2026-04-22

## 目的

アプリケーションの主要コンポーネントと責務分割の方針を決める。

## 背景

ドメインが広いため、初期段階からモジュール境界を意識しないと複雑化しやすい。

## 前提

- MVP は開発速度も重視する
- MVP と第 2 フェーズでは運用複雑性を増やしすぎない
- 将来は `WorkHistory`, 監査, 検索, AI 要約の追加を見据える

## 決定事項

- MVP と第 2 フェーズのアプリケーション分割方針は `モジュラモノリス` を第一候補とする
- アプリケーションは `1 つのデプロイ単位` で運用しつつ、コード上は明確なモジュール境界を持つ
- 初期段階では同期的なアプリケーションフローを基本とし、非同期処理は限定用途に絞る
- 認可はアプリケーション層で一元化し、`RBAC + 組織スコープ` を共通ルールとして扱う

### `モジュラモノリス` のこのプロジェクトでの意味

このプロジェクトでいう `モジュラモノリス` は、アプリケーション全体は 1 つとして動かしながら、コードの責務境界を先に分けておく構成を指す。

現時点の第一候補モジュールは以下。

- `employee-directory`
  - 社員台帳、表示用プロフィール、顔写真参照
- `organization-management`
  - 組織、組織階層、`OrganizationLeader`
- `employment-management`
  - 主所属、兼務、上長、在籍状態
- `authorization`
  - `RoleAssignment`, スコープ判定, テナント境界
- `work-history`
  - `WorkHistory` の登録、更新、公開判定
- `audit`
  - `LoginHistory`, `EditHistory`

この段階では、上記は別サービスではなく同一アプリケーション内のモジュールとして実装する。

### この判断の理由

- MVP と第 2 フェーズでは、サービス分割よりも機能の正しさと実装速度が重要
- 最初からマイクロサービスにすると、認証, 監視, デプロイ, サービス間通信, データ整合の負荷が先に大きくなる
- 一方で、単なる巨大な単一アプリにすると、後続の `WorkHistory` や監査追加で責務が混ざりやすい
- そのため、初期は `1 つのアプリ + 明確なモジュール境界` の方が現実的

## 検討した選択肢

- モジュラモノリス
- 小規模マイクロサービス
- BFF を含む分離構成

### 1. モジュラモノリス

利点:

- デプロイ, 開発, ローカル実行, 障害切り分けが比較的単純
- ドメイン境界を先に切れるため、将来の分離余地を残せる
- 認可やテナント境界の一元化がしやすい

欠点:

- モジュール境界を甘くすると、単なる大きな単一アプリに崩れやすい
- チーム拡大後は独立リリースしづらい

### 2. 小規模マイクロサービス

利点:

- モジュール単位で独立デプロイしやすい
- チーム分業には向く

欠点:

- 今の段階では運用複雑性が過剰
- テナント境界, 認証, 認可, 監査を各サービスでそろえる負荷が大きい

### 3. BFF を含む分離構成

利点:

- UI 向け最適化はしやすい

欠点:

- MVP 段階では構成要素が増えすぎる
- バックエンドの中心設計が固まる前に導入する意義が薄い
