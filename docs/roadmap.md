- Status: Draft

## 目的

この文書は、プロジェクト全体のゴール、現在地、フェーズ、マイルストーンを一枚で把握できるようにするための進行管理ハブである。

人間の担当交代、別 AI への引き継ぎ、同じ AI のセッション再開時にも、この文書を見れば「何を目指していて、今どこで、次に何を決めるか」が分かる状態を目指す。

## 背景

このプロジェクトは、カオナビやタレントパレットのようなタレントマネジメントサービスを、必要機能を絞ってベータへ早く到達する方針で設計している。

ただし、設計論点が多いため、`MVP`、`第2フェーズ`、`将来拡張` が混ざると全体像を見失いやすい。そこで、段階ごとのゴールと判断対象を明確に分けて管理する。

## 前提

- 初期ターゲットは `100 名から 500 名規模の企業`
- 主担当ユーザーは `人事部門 + 管理職`
- 経営層は初期フェーズでは閲覧中心
- MVP の中心ユースケースは `社員台帳と組織図の一元管理`
- 一般社員向け機能は将来重要だが、最初から全部は入れない
- スコープや優先順位の確定は必ず Keith に確認する

## ゴール

### 最終的に目指すプロダクト

- 人材情報を単に保存するのではなく、組織内の意思決定に使える状態へ整える
- 人事、管理職、一般社員が、権限に応じて人材情報を閲覧・更新できる
- 将来的に、業務履歴やスキル情報から AI が要約、助言、相談チャットを行える

### 直近の到達目標

- ベータに到達できる最小スコープを定義する
- そのベータを実装可能な粒度まで、プロダクト設計と技術設計を固める

## 現時点の確定事項

- 初期ターゲットは `100 名から 500 名規模の企業`
- 主担当ユーザーは `人事部門 + 管理職`
- MVP は `社員台帳と組織図の一元管理`
- 中心モデルは `Employee`, `Organization`, `Employment`, `RoleAssignment`, `OrganizationLeader`
- 兼務は `Employment` の複数レコードで扱う
- 兼務は別組織所属よりも、同一組織内の役割兼任や案件兼務を中心に扱う
- 権限モデルは `RBAC + 組織スコープ`
- MVP と第 2 フェーズのアプリケーション構成は `モジュラモノリス` を第一候補とする
- 認可はアプリケーション層で `RBAC + 組織スコープ` を一元的に扱う
- 主要データストアは `PostgreSQL` を第一候補とする
- 初期の認証方式は `アプリ内認証で開始し、後で SSO を追加する方式` を第一候補とする
- `MVP` はアプリ内認証のみを第一候補とし、`第 2 フェーズ` でも SSO は必須にしない
- SSO は、顧客要件または導入運用上の必要性が明確になった時点で `第 3 フェーズ以降` の追加候補とする
- メール送信基盤は初期外部システムに含めず、必要になった時点で追加する
- `ORG_ADMIN` は役職と独立したロール
- 顔写真は本番でオブジェクトストレージ、開発でローカルファイル保存も許容
- 履歴は `Employment` と `OrganizationLeader` を中心に持つ
- 論理削除社員の閲覧・復元は `ORG_ADMIN` のみ
- `profile_free_text` は MVP に含める
- `profile_free_text` は本人に加えて `HR_ADMIN` と `MANAGER` が補助更新できる
- `profile_free_text` の Markdown はオプション機能として第 2 フェーズで扱う
- 第 2 フェーズでは Markdown の入力保存を先に扱い、表示時の Markdown レンダリングは第 3 フェーズ以降の候補とする
- `WorkHistory` は第 2 フェーズで導入し、完成形では必須機能とする
- `WorkHistory` は本人に加えて `HR_ADMIN` と `MANAGER` が補助編集できる
- `WorkHistory` は同僚も閲覧できる前提とする
- `WorkHistory` は最初から `updated_by` を持つ
- `WorkHistory` の原文表示期間の初期値は `1 年 (365 日)` とする
- `WorkHistory` の AI サマリは、本人の業務履歴要約とスキルアピール文の自動生成を目的とする
- AI サマリは本人以外にも公開してよい情報として扱う
- 同僚には、直近期間までは `WorkHistory` の原文を表示し、それ以前は AI サマリを表示する
- 本人、`HR_ADMIN`、`MANAGER` は期間単位のページングで `WorkHistory` の原文を全件閲覧できる
- `WorkHistory` の AI サマリは第 3 フェーズ以降の拡張候補とする
- `WorkHistory` の AI サマリは `フェーズ 3` の対象とする
- AI アドバイス文、AI 相談チャット、AI 検索 / 推薦は `フェーズ 4` の対象とする
- `WorkHistory` の AI サマリを `フェーズ 3` に入れる前提条件は、`WorkHistory` 入力運用、原文閲覧ルール、監査ログ運用が最低限安定していることとする
- `フェーズ 4` の優先順位は、`AI 検索 / 推薦` → `AI アドバイス文` → `AI 相談チャット` とする
- `AI 検索 / 推薦` は必要機能として扱うが、AI を使うか通常検索拡張で始めるかは現時点では確定しない
- `WorkHistory` の AI サマリは登録・更新時に再生成し、履歴全体サマリとツール・技術一覧を出せる形を目指す
- AI サマリの文字数は設定値で持ち、実装後に調整できる形を第一候補とする
- 初期推奨値として、キャリアサマリは `180〜280 文字`、スキルアピール文は `70〜120 文字` を目安とする
- AI サマリの表示順は、`キャリアサマリ` → `スキルアピール文` → `ツール・技術一覧` を第一候補とする
- `WorkHistory` は履歴書出力を見据え、自由装飾よりも構造化入力を優先する
- `LoginHistory` と `EditHistory` は第 2 フェーズで導入する推奨とする
- `LoginHistory` と `EditHistory` の閲覧は `HR_ADMIN` のみに許可する前提とする
- `EditHistory` の対象エンティティ第一候補は `Employee`, `Employment`, `OrganizationLeader`, `WorkHistory`, `RoleAssignment` とする
- マルチテナント方式は、共有テーブル型を基本にしつつ、単一テナント専用デプロイにも対応できる方式を第一候補とする
