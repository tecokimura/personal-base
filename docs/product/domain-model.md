# Domain Model

- Status: In Review
- Owner: Keith / Codex

## 目的

サービス内で扱う中心エンティティと関係を整理する。

## 背景

タレントマネジメントでは、社員、組織、評価、スキル、異動、役職などが強く関連する。ここが曖昧だと後続の設計が崩れる。

ただし、今回の MVP は `社員台帳と組織図の一元管理` に絞っているため、最初からすべてのドメインを同じ深さで持つべきではない。まずは MVP を成立させる最小の中心モデルを定義し、その後にスキル、業務履歴、評価へ拡張できる形を目指す。

## 前提

- 社員情報が中核エンティティになる
- 将来的に履歴管理が必要になる可能性が高い
- MVP の中心ユースケースは `社員台帳と組織図の一元管理`
- 主担当ユーザーは `人事部門 + 管理職`
- 一般社員向け機能、スキル、評価、AI 助言は後続フェーズで拡張する余地を持つ

## 決定事項

- MVP の中心エンティティは `Employee`, `Organization`, `Employment`, `RoleAssignment` とする
- MVP では組織責任者を表すために `OrganizationLeader` を追加する
- `Employee` を社員本人の基本単位とし、組織所属や権限は別概念として切り分ける
- `Organization` は組織図を表す階層構造として扱う
- 雇用情報や在籍状態は `Employee` にべた書きせず、`Employment` として独立させる
- MVP でも兼務を扱う
- `Employee` には、自己紹介や業務概要を自由に書ける `profile_free_text` を持たせる
- 役職は自由文字列ではなく、マスタ化を前提とする
- `Job Grade` は役職と同義にしない限り将来は独立候補だが、MVP では持たない
- 権限や閲覧ロールは、将来の認可設計に接続しやすいよう `RoleAssignment` として独立させる方針とする
- `WorkHistory` は MVP の主要エンティティからは外すが、完成形では必須の後続拡張エンティティとして扱う
- `Evaluation`, `SkillProfile` は後続拡張エンティティ候補として扱う

## 検討した選択肢

### 1. すべてを `Employee` に集約して持つ

社員テーブルに所属、役職、状態、権限まで寄せる案。初速は速いが、異動、兼務、履歴、権限スコープで破綻しやすい。

### 2. MVP に必要な概念だけ分ける

`Employee`, `Organization`, `Employment`, `RoleAssignment` を分ける案。MVP ではやや設計コストが上がるが、後続拡張に耐えやすい。

### 3. 最初から履歴イベント中心で設計する

異動、組織改編、権限変更をイベントとして強く持つ案。将来性は高いが、初期実装には重すぎる。

現時点では、`2. MVP に必要な概念だけ分ける` を第一候補とする。

理由:

- MVP の単純さと将来拡張のバランスがよい
- `社員台帳と組織図` の実装に必要な単位が明確になる
- 後からスキル、評価、業務履歴を追加しても破綻しにくい

## `WorkHistory` の最小仕様たたき台

`WorkHistory` は MVP の外に置くが、完成形では必須機能とする。そのため、後続で大きく破綻しないように最小仕様を先に置いておく。

### 目的

- 社員本人が、自分のこれまでの仕事や履歴を登録、更新、確認できるようにする
- 管理職や同僚が、その社員の担当経験を把握できるようにする
- 将来の AI 要約や人材検索の元データにする

### 最小単位

- `1 人の社員` に対して `複数件` の `WorkHistory` を持てる
- 各履歴は、1 つの案件、担当期間、または一定期間の業務担当を表す

### 第 2 フェーズの第一候補の項目

- `employee_id`
- `year_month_from`
- `year_month_to`
- `is_current`
  - 現在進行中かどうか
- `work_summary`
  - 業務内容の自由記述
- `tech_stack_or_tools`
  - 開発環境、利用技術、主要ツールの記述
- `role_name`
  - その履歴での役割名
- `team_size`
  - 関与した開発チーム人数を表す数値
- `updated_by`
  - 最終更新者を保持する
- `updated_at`
  - 最終更新日時を保持する

### 第 2 フェーズで任意とする第一候補の項目

- `project_code`
  - 社内案件や管理番号がある場合に使う

### 第 2 フェーズでは外す第一候補の項目

- `organization_name_snapshot`
  - 当時所属していた組織名のスナップショットは後続候補とする
- `visibility_scope`
  - レコード単位の公開範囲制御は第 2 フェーズでは持たない
- `sort_order`
  - 表示順は新しい順固定を前提とし、手動並び替えは持たない
- `created_by`
  - 初回登録者の保持は後続候補とする

### 第一候補の運用ルール

- 社員本人が登録、更新できる前提とする
- `HR_ADMIN` と `MANAGER` は補助編集できる前提とする
- 長文の案件日報ではなく、振り返って参照できる業務履歴として扱う
- 期間は日付ではなく、まず `年月` 単位で持つ
- `year_month_to` が空で `is_current = true` の場合は現在進行中とみなす
- 表示順は、新しい順を基本とする
- `tech_stack_or_tools` はタグ化ではなく、まずは自由記述でも成立する形を許容する
- `team_size` は開発チーム人数を表す数値として扱う
- `project_code` は、必要な顧客だけが使える自由入力項目として扱う
- 本人以外の補助編集を許可するため、`updated_by` は最初から保持する
- `updated_at` も最初から保持し、補助編集時刻を追えるようにする
- 同僚公開はレコード単位の公開/非公開切替を持たず、第 2 フェーズでは一律ルールで扱う
- `created_by` は必要性が見えた時点で後続追加する

## 社員番号の生成/初期値ルールたたき台

このサービスでは、`Employee ID` を内部識別子、`社員番号` を業務上の表示番号として分けて扱う前提にする。

この分離は重要である。

- `Employee ID` はシステム内部で不変
- `社員番号` は顧客企業の運用や雇用区分に応じて変わりうる
- 社員番号未設定者、契約社員、例外社員も扱える必要がある

### 選択肢 1. 社員番号を必須・一意で自動採番する

利点:

- 見た目がそろう
- 初期データが作りやすい

欠点:

- 顧客側の既存番号体系と衝突しやすい
- 未設定者や特例社員の扱いが硬直化する

### 選択肢 2. 社員番号を任意入力にし、未設定を許容する

利点:

- 既存運用に合わせやすい
- 契約社員や外部人材を柔軟に扱える

欠点:

- 未設定データが増える可能性がある
- 一覧上の見栄えがばらつく

### 選択肢 3. 社員番号は任意入力だが、未設定時はプレースホルダを自動付与する

例:

- `TEMP-000001`
- `EXT-000123`
- `CNTR-000045`

利点:

- 未設定を放置しなくて済む
- 契約社員や特例社員に暫定番号を振りやすい
- CSV 取込時にも扱いやすい

欠点:

- 顧客によっては暫定番号が業務番号として誤認される
- プレースホルダの命名ルールを設計する必要がある

### 現時点の第一候補

MVP では、`選択肢 3` を第一候補とする。

具体方針候補:

- `Employee ID` はシステム発番の不変 ID とする
- `社員番号` は業務表示用の項目として持つ
- 既存番号がある場合はその値を優先する
- 未設定の場合はプレースホルダ番号を自動付与する
- 契約社員など特殊区分には、区分を識別できる接頭辞を許容する
- `社員番号` は数値ではなく文字列として扱う

### プレースホルダ番号の第一候補

- 正社員未設定: `TEMP-000001`
- 契約社員系: `CONT-000001`
- 外部人材系: `EXT-000001`

この接頭辞は、最終的には顧客設定可能にしてもよいが、MVP では固定でもよい。

### 接頭辞の意味

- `TEMP`
  `Temporary` の略。正式な社員番号が未設定な暫定番号を表す。
- `CONT`
  `Contract` の略。契約社員など契約系区分の暫定番号を表す。
- `EXT`
  `External` の略。外部人材、外部協力者、受入出向者など、通常社員番号体系と分けたい人材の暫定番号を表す。

### 雇用区分との関係

- 正社員で正式番号がある場合は、その正式番号を使う
- 正社員で正式番号が未設定の場合は `TEMP` を使う
- 契約社員系で正式番号が未設定の場合は `CONT` を使う
- 外部人材系で正式番号が未設定の場合は `EXT` を使う

### データ制約の第一候補

- `Employee ID` は必須かつ一意
- `社員番号` はテナント内で一意
- `社員番号` は未設定不可とし、未設定時は自動でプレースホルダを入れる
- プレースホルダ番号も通常番号と同じく一意制約対象にする

### 現時点の考え方

- 社員番号は人間向けの業務番号であり、システム主キーには使わない
- 顧客既存番号の取込を優先する
- 未設定者を扱えることを優先し、欠損ではなく暫定値で埋める
- 後から正式番号に差し替えても、内部参照は `Employee ID` により壊れない
- 接頭辞の意味は文書に残し、将来見返しても意味不明な略称にならないようにする

## 組織責任者の表現たたき台

組織図と権限モデルを安定させるには、「その組織の責任者」をどう持つかを明確にする必要がある。

### 選択肢 1. `Organization` に直接持つ

例:

- `Organization.manager_employee_id`

利点:

- 実装が単純
- 組織図表示にそのまま使いやすい
- `MANAGER` の基本スコープ判定に利用しやすい

欠点:

- 責任者履歴を細かく持ちにくい
- 複数責任者には向かない
- 将来、責任者種別が増えると拡張が苦しくなる

### 選択肢 2. 別の関係エンティティで持つ

例:

- `OrganizationLeader`
  - Organization ID
  - Employee ID
  - Leader Type
  - Start Date
  - End Date

利点:

- 履歴を持ちやすい
- 複数責任者や責任者種別に対応しやすい
- 将来拡張に強い

欠点:

- MVP としては設計が一段重くなる
- 組織図や権限判定の参照が増える

### 現時点の第一候補

MVP では、`OrganizationLeader` のような別関係エンティティで組織責任者を持つことを第一候補とする。

理由:

- 組織責任者が複数人になる可能性を最初から扱える
- 責任者履歴を持ちやすい
- 兼務や役職者の兼任という今回の前提に合う

### 将来拡張時の考え方

- MVP でも `OrganizationLeader` を使う
- 将来は `LeaderType` や履歴管理を拡張する
- アプリケーション側では「主責任者」と「複数責任者」を使い分けられるようにする

## 兼務ルールたたき台

MVP でも兼務を扱う前提なので、`Employment` を単なる所属情報ではなく、「社員と組織の関係」を表す単位として扱う。

### 基本方針候補

- 1 人の社員は複数の `Employment` を持てる
- `Employment` ごとに所属組織、役職、上長、状態を持てる
- そのうち 1 件を `主所属` とし、残りを `副所属` とする
- `主所属` は 1 件のみ許可する
- `副所属` は複数件を許可する

### 主所属の扱い

主所属は、以下の基準に使う第一候補とする。

- 社員一覧のデフォルト表示組織
- 組織図での主な所属先
- 権限判定時の基本スコープ
- 人事管理上の代表所属

### 副所属の扱い

副所属は、以下の用途で扱う。

- 兼務先組織への所属表示
- 管理職による兼務メンバー把握
- 将来の権限制御や業務履歴との接続

MVP では、副所属について高度な重み付けや工数配分までは持たない。

また、このプロジェクトで想定する兼務は、別組織をまたぐ所属よりも、同一組織内での役割兼任や他部署案件の兼務が中心である。この前提により、兼務は別組織への閲覧権限拡大の起点ではなく、社員の担当範囲や役割重複を表す情報として扱う。

### 上長の扱い

- `Manager Employee ID` は `Employment` ごとに持つ
- これにより、主所属と副所属で別の上長を設定できる
- `Employee` にも直属上長相当の参照を置く余地はあるが、MVP では持たない
- MVP の上長情報の正本は `Employment.Manager Employee ID` とする

### 組織図での見え方

- 組織図の標準表示では、社員は `主所属` に加えて `副所属` も見えるようにする
- ただし、表示上は `主所属` と `兼務` が識別できる必要がある
- 組織詳細画面では副所属メンバーも一覧できるようにする
- 副所属メンバーの表示は全社設定で ON/OFF 切替できるようにする

### データ制約の第一候補

- 同一社員に `Is Primary Assignment = true` の `Employment` は 1 件のみ
- 同一社員は同一組織に対して、有効期間が重複する同種の `Employment` を重複登録しない
- `Manager Employee ID` は原則として同一テナント内の有効な社員を参照する

### MVP でやらないこと

- 兼務比率の管理
- 主所属の自動切替ルール
- 複雑な兼務優先順位
- 兼務ごとの詳細権限カスタマイズ

### 現時点の第一候補

現時点では、以下を第一候補とする。

- 兼務は `Employment` の複数レコードで表現する
- `Is Primary Assignment` で主所属を 1 件だけ示す
- 組織図の標準表示では主所属と副所属の両方を見せる
- ただし、表示ラベルは `主所属` と `兼務` を使って区別する
- 副所属メンバーは組織詳細画面でも表示し、全社設定で ON/OFF 切替できる
- 上長の正本は `Employment.Manager Employee ID` に持つ
